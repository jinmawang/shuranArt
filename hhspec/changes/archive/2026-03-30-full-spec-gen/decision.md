# 关键决策：full-spec-gen

## 决策 1：课程管理数据方案
- **选择**：动态后台 CRUD 管理（新建 course 数据库表 + 管理页面）
- **理由**：参照已有 Teacher 管理模式，开发成本可控，管理员可灵活维护课程信息
- **备选**：
  - 静态配置（前端写死）— 否决：无法灵活更新
  - 复用 studio_config 表 — 否决：JSON 结构不够清晰，不利于分类筛选

## 决策 2：分享海报技术方案
- **选择**：前端 Canvas 2D API 绘制
- **理由**：零服务器成本，Canvas 2D 在基础库 2.9.0+ 广泛支持（覆盖率 >99%）
- **备选**：
  - 后端图片合成 — 否决：需要图片存储服务和服务器渲染成本
  - 仅使用微信原生分享 — 否决：无法覆盖朋友圈和非微信场景

## 决策 3：限界上下文归属
- **选择**：复用现有上下文
  - CRS → 画室上下文（与 Teacher、StudioConfig 同属）
  - PST → 分享上下文（与 ShareRecord 同属）
  - EXC → 兑换上下文（独立，已规划）
- **理由**：项目规模小，新功能与现有上下文职责匹配，无需增加上下文复杂度
- **备选**：全部独立上下文 — 否决：过度拆分，增加认知负担

## 决策 4：积分扣减原子性
- **选择**：使用 SQL 条件更新（`UPDATE user SET points = points - ? WHERE id = ? AND points >= ?`）
- **理由**：通过 affected rows 判断是否成功，避免 read-then-write 竞态条件，无需额外锁机制
- **备选**：应用层加锁 — 否决：增加复杂度，单机部署无需分布式锁

## 决策 5：微信 access_token 管理
- **选择**：后端新增 access_token 获取和缓存机制
- **理由**：小程序码生成需要 access_token，当前系统不具备。使用内存缓存 + 2小时自动刷新
- **备选**：每次调用时获取 — 否决：频繁调用可能触发微信 API 限流

## 决策 6：课程分类方案
- **选择**：硬编码在前端（素描、水彩、油画、国画等预设类别）
- **理由**：画室课程类别相对固定，硬编码足够；后期如需求变化可迁移到配置表
- **备选**：后台可配置分类 — 否决：当前需求简单，过度设计

## 决策 7：海报尺寸
- **选择**：固定 750x1334px（iPhone 逻辑分辨率）
- **理由**：主流手机屏幕适配良好，图片文件大小合理，Canvas 绘制性能可控
- **备选**：根据屏幕动态计算 — 否决：增加复杂度，不同尺寸海报视觉效果难以统一

## 决策 8：实施顺序
- **选择**：CRS + PST 并行 → EXC → 首页布局统一调整
- **理由**：CRS 完全独立无依赖；PST 依赖已有数据但需新增 access_token；EXC 涉及积分事务最复杂；最后统一调整首页和管理后台入口布局
